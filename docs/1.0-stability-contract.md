# TelegramJ2ME 1.0 stability contract

Version 1.0 means a bounded, usable text client on CLDC 1.1 / MIDP 2.0. It is
not a promise of complete Telegram feature coverage, background notifications,
media sending, secret chats, or a security audit.

## What 1.0 guarantees

- Existing 0.8.1 production installations are upgraded in place: the MIDlet
  name remains `TelegramJ2ME`, the vendor remains `smbdsbrain`, and the build
  environment remains `production`, so the AMS keeps the suite's RMS stores.
- The application version in the manifest and JAD is `1.0.0`; RC filenames do
  not change that suite version.
- Text workflows are bounded: dialog/history paging, send/outbox, reply,
  forward, delete, in-chat search, full text, supported entities, and editing
  eligible own outgoing text.
- Network, update, cache, and callback failures preserve user-owned state or
  fail visibly. There is no unbounded request queue, result list, entity list,
  history, dialog list, or cache.
- Both normal and minified artifacts compile for Java source 1.3, pass the CLDC
  public-API audit, contain CLDC StackMap data, and start in packaged
  MicroEmulator smoke under a 32 MiB host ceiling.
- No development report endpoint, collector token, private MTProxy endpoint, or
  proxy secret is embedded in an RC. The build refuses `-EmbedDevSecrets` for
  every artifact name beginning `TelegramJ2ME-`.

The scenario-by-scenario evidence is the
[1.0 failure matrix](testing/1.0-failure-matrix.md). A row stays `NOT RUN` until
its exact tier has produced evidence; a desktop fault injector is not hardware
flash evidence, and an older handset session is not a 1.0 RC run.

## Cache and upgrade boundary

Dialog cache remains v1. History cache evolved additively:

| Version | Contents | Current reader |
|---|---|---|
| v1 | bounded message core | readable; entities and edit date default empty |
| v2 | v1 plus bounded entities | readable; edit date defaults to zero |
| v3 | v2 plus message edit date | current write format |

The caches are server-owned copies and may be discarded and refetched if
corrupt. Auth keys, outbox records, drafts, settings, and update cursors follow
their own durable formats and are not discarded as part of this migration.

Downgrading after 1.0 is not supported: 0.8.1 does not understand history cache
v3 and may discard it. It should still keep the session and other compatible
RMS records, but users should not treat downgrade cache retention as a promise.

## Schema boundary

The 1.0 artifacts advertised and generated from pinned Telegram layer 223.
Current builds deliberately moved to layer 225 using the reviewed official
Telegram Desktop TL source because the public JSON endpoint still serves the
older document. The historical 1.0 artifacts remain reproducible; current
provenance and hashes are in [schema/UPSTREAM.md](../schema/UPSTREAM.md).

The multi-gather auth-key seeding work tracked by
[GitHub issue #2](https://github.com/smbdsbrain/TelegramJ2ME/issues/2) is closed
and covered by the deterministic seeding tests and recorded handset
measurements. This does not turn TelegramJ2ME into a security-audited client;
the remaining entropy caveats in the architecture document still apply.

## Release-candidate handoff rule

The required order is:

1. deterministic stability gate;
2. build `TelegramJ2ME-1.0.0-rc1` normal and minified production pairs;
3. offline packaged smoke of both RC JARs with `-Xmx32m`;
4. read-only and marked two-account E2E on both saved emulator profiles, first
   normal and then minified;
5. repeat both exact packaged variants with `-Xmx32m`, deterministic slow and
   fragmented MIDP socket I/O, and the reaction loading/Back/foreground race;
6. JAD/JAR consistency, SHA-256, artifact sizes, public audit, and clean Git;
7. hand the normal pair to the user as the Nokia upgrade candidate and the
   minified pair as fallback.

Any mandatory emulator failure blocks handoff and restarts the final gate after
the defect is fixed. No tag and no GitHub Release are created until the user has
completed the Nokia C3-00 upgrade run and supplied the evidence outcome.
